# Восстановление удалённых файлов APFS вне дерева каталогов (APFS Salvage)

## Обзор и назначение

Apple File System (APFS) использует парадигму Redirect-on-Write (RoW) с транзакционной моделью чекпоинтов. При удалении файла или каталога в рабочей системе:
1. Записи инода (`j_inode_key_t`, `j_inode_val_t`), файловых экстентов (`j_file_extent_key_t`, `j_file_extent_val_t`) и каталога (`j_drec_key_t`, `j_drec_val_t`) исключаются из активного корневого B-Tree тома (`apfs_root_tree_oid`).
2. Новые версии узлов дерева B-Tree записываются в новые блоки контейнера.
3. Исторические листовые узлы B-Tree, содержавшие метаданные удалённого файла, остаются физически нетронутыми в блоках контейнера вплоть до их повторного выделения (allocation).
4. Стандартные инструменты восстановления и драйверы ОС, обходящие только активное дерево каталогов или снимки (snapshots), не видят удалённые файлы вне снимков.

Модуль `UsbRecovery.ApfsRecovery` (`src/Recovery/Recovery/Engines/ApfsRecovery.cs`) реализует независимое от внешних библиотек и полностью безопасное в памяти C# восстановление удалённых файлов APFS путём глубокого сканирования контейнера, верификации контрольных сумм Fletcher-64 и сопоставления свободных/исторических экстентов.

## Архитектура и структуры данных APFS

### 1. Заголовок объекта (`obj_phys_t`)
Каждый метаданный блок APFS (размером 4096 байт) начинается со стандартного заголовка `obj_phys_t`:
- `o_cksum` (8 байт, смещение 0): 64-битная контрольная сумма Fletcher-64, вычисляемая от смещения 8 до конца блока.
- `o_oid` (8 байт, смещение 8): идентификатор объекта (Object ID).
- `o_xid` (8 байт, смещение 16): номер транзакции (Transaction ID).
- `o_type` (4 байта, смещение 24): тип объекта (`OBJECT_TYPE_NX_SUPERBLOCK = 1`, `OBJECT_TYPE_BTREE = 2`, `OBJECT_TYPE_BTREE_NODE = 3`, `OBJECT_TYPE_FS = 13`). Флаги верхних бит: `OBJ_PHYSICAL = 0x40000000`, `OBJ_EPHEMERAL = 0x80000000`.
- `o_subtype` (4 байта, смещение 28): подтип объекта (`0x0E` / 14 для записей файловой системы).

### 2. Контрольная сумма Fletcher-64
В соответствии со спецификацией Apple File System Reference, контрольная сумма Fletcher-64 вычисляется по 32-битным словам:
$$\text{sum}_1 = \sum w_i \pmod{2^{64}}$$
$$\text{sum}_2 = \sum \text{sum}_1 \pmod{2^{64}}$$
Конечные 32-битные половины:
$$ck_{\text{low}} = 0xFFFFFFFF - ((\text{sum}_1 + \text{sum}_2) \pmod{0xFFFFFFFF})$$
$$ck_{\text{high}} = 0xFFFFFFFF - ((\text{sum}_1 + ck_{\text{low}}) \pmod{0xFFFFFFFF})$$
Итоговое значение: $ck = ck_{\text{low}} \mid (ck_{\text{high}} \ll 32)$.

Все повреждённые блоки с несовпадающим Fletcher-64 отбраковываются с фиксацией в `CorruptedNodesSkipped`.

### 3. Листовой узел B-Tree (`btree_node_phys_t`)
- `btn_flags`: флаги узла (0x0001 = ROOT, 0x0002 = LEAF, 0x0004 = FIXED_KV_SIZE).
- `btn_level`: уровень узла (0 = листовой узел).
- `btn_nkeys`: количество ключей.
- `btn_table_space`: смещение и длина таблицы оглавления (TOC).
- Массив `kvloc_t` в TOC: для каждого элемента содержит `k.off`, `k.len`, `v.off`, `v.len`.
  - Ключи растут от смещения `56 + table_space.off + table_space.len`.
  - Значения растут снизу вверх от `blockSize - (40 if root else 0) - v.off`.

### 4. Ключи и значения записей файловой системы
Старшие 4 бита ключа (`rawKey >> 60`) задают тип записи:
- **Тип 3 (INODE)**: ключ содержит `obj_id`. Значение `j_inode_val_t`:
  - `parent_id` (смещение 0), `private_id` (смещение 8).
  - Временные метки в наносекундах (`create_time`, `mod_time`, `change_time`, `access_time`).
  - `mode` (смещение 80): тип файла (0x8000 = обычный файл, 0x4000 = каталог).
  - `uncompressed_size` (смещение 84): логический размер файла.
  - Расширенные поля (`xfields`): `NAME` (тип 4, имя файла), `DSTREAM` (тип 8, размер потока данных и выделенный объём).
- **Тип 8 (FILE_EXTENT)**: ключ содержит `obj_id` (inode или private_id) и логическое смещение `logical_addr`. Значение `j_file_extent_val_t`:
  - `len_and_flags` (8 байт): длина экстента в байтах (`len & 0x00FFFFFFFFFFFFFF`).
  - `phys_block_num` (8 байт): физический номер начального блока в контейнере.
  - `crypto_id` (8 байт): ключ шифрования.
- **Тип 9 (DIR_REC)**: ключ содержит `parent_id` и имя файла в UTF-8. Значение `j_drec_val_t`:
  - `file_id` (8 байт): номер инода целевого файла.
  - `date_added` (8 байт): дата добавления.
  - `flags` (2 байта): атрибуты файла.

## Алгоритм восстановления `ApfsRecovery`

1. **Инициализация и проверка неизменности**:
   - Вычисление исходного SHA-256 входного образа.
   - Проверка блокировки повторной записи и проверка каталога назначения.
2. **Обнаружение контейнера и томов**:
   - Поиск суперблока контейнера `NXSB` в блоке 0 (с fallback-сканированием начальных блоков).
   - Определение размера блока контейнера (по умолчанию 4096 байт) и общего количества блоков.
   - Сканирование блоков на наличие суперблоков томов `APSB` (смещение 32) с валидацией Fletcher-64.
3. **Обход живого дерева (Surviving Tree Traversal)**:
   - Обход корневого B-Tree тома (`apfs_root_tree_oid`).
   - Сбор идентификаторов активных файлов в `liveOids`.
4. **Сквозное сканирование контейнера (Historical Sweep)**:
   - Проверка каждого блока контейнера на соответствие заголовку B-Tree узла (`o_type` 2 или 3, `o_subtype` 14).
   - Верификация Fletcher-64.
   - Извлечение всех инодов, экстентов и записей каталогов, включая принадлежащие предыдущим транзакциям.
5. **Ассоциация и сборка экстентов**:
   - Разделение на живые файлы (`recovered_live`) и удалённые кандидаты (`deleted_apfs_unreferenced_candidate`).
   - Сопоставление экстентов по `private_id` и `ObjectId` с выбором наиболее актуальной непротиворечивой версии по `xid`.
   - Упорядочение экстентов по `LogicalOffset`.
   - Реконструкция пути каталогов из родительских `drec` или размещение сирот в `[Lost+Found]`.
   - Потоковое извлечение полезной нагрузки из физических блоков контейнера с расчётом SHA-256.
6. **Контроль ресурсов и отчётность**:
   - Соблюдение лимитов `MaximumFileBytes`, `MaximumOutputBytes`, `MaximumDirectories`.
   - Формирование отчёта `apfs/report.json` со статусом, доказательствами удаления (`DeletionEvidence = "unreferenced_in_live_btree"`), матрицей возможностей и хэшами.
   - Подтверждение сохранения исходного хэша образа (`SourceUnchanged = true`).

## Проверка и доказательная база

Тестовый набор `tests/ApfsRecoveryTests.cs` (169 проверок) подтверждает:
- Точное извлечение файлов из живого дерева тома.
- Восстановление удалённых файлов из свободных блоков вне живого дерева с точным совпадением SHA-256.
- Сборку фрагментированных файлов с нелинейным расположением экстентов.
- Восстановление файлов-сирот без `drec` через поле `NAME` и fallback `[Lost+Found]`.
- Реконструкцию удалённой иерархии подкаталогов.
- Отбраковку блоков с повреждёнными суммами Fletcher-64 без сбоев.
- Соблюдение границ ресурсов и прерывание по `CancellationToken`.
