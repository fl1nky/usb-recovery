# APFS: структурный поиск и продолжение

В программе есть два отдельных пути APFS. Этот документ описывает C# `ApfsRecovery`, который запускается способом «Записи и метаданные APFS». Python `storage_apfs` для чтения контейнеров и снимков имеет собственные проверки; их результаты не подтверждают этот структурный парсер.

## Что делает управляемый парсер

Парсер проверяет поддержанные заголовки NXSB/APSB и листовые записи с Fletcher-64, связывает найденные inode, записи каталогов и экстенты. Он работает с образом только для чтения. Переданные смещения контейнеров учитываются при чтении метаданных и данных; байтовые смещения в отчёте относятся к исходному образу.

`recovered_live` — сохранённое имя категории для записи, обнаруженной при поддержанном чтении корневого узла. Полный обход активного дерева и распределение блоков этим не устанавливаются. `unreferenced_apfs_candidate` означает структурную запись вне проверенной части корня. Такая запись сама по себе не доказывает удаление, свободное состояние блоков или принадлежность содержимого прежнему файлу.

У всех кандидатов `ContentAuthenticityVerified=false` и `DeletionEvidence=null`. SHA-256 фиксирует полученный результат. Контрольная сумма метаданных не удостоверяет подлинность файловых данных.

## Продолжение и сохранность

Штатный `RecoveryPipeline` использует `RecoverCheckpointed`. Корневой журнал связывает образ, сборку, параметры, смещения, карты ошибок и папку результата. Общий `RecoveryMetadataReads` сохраняет подтверждённые исходные чтения; при повторном запуске парсер пересобирает структуры из этих байтов. Завершённые файлы проверяются, пропавшие результаты ремонтируются через отдельные дочерние позиции. Финальный отчёт проходит стадию ожидания публикации.

`RecoveryVerifiedImage` удерживает проверенный источник с запретом записи. В рамках одного вызова дочерние операции используют этот объект вместо повторного хэширования всего образа для каждого файла. После нового запуска полный SHA проверяется заново. Отсутствие повторных вычислений или любого повторного чтения вообще не обещается.

Результаты находятся в `apfs/files`; `apfs.state` содержит служебные данные продолжения. Оба каталога входят в область сеанса. Исходные имена остаются данными отчёта, а имена на Windows очищаются и включают идентификаторы объекта/транзакции. Публикация не перезаписывает существующий файл. Неполная карта, логические перекрытия и выход за источник завершаются ошибкой. Цикл родителей не запускает неограниченную рекурсию.

## Проверки и границы

Шесть закреплённых примеров `tests/fixtures/apfs-salvage` созданы собственным генератором. Они проверяют реализацию, но не являются независимыми томами, созданными macOS. Native-совместимость этого управляемого парсера, шифрование, сжатие, все object-map layouts, snapshots и полное восстановление удалённых файлов ими не подтверждены.

Проверки разделены на регрессии парсера, безопасность выходных файлов, внутреннее продолжение и обычный `RecoverySession`. Контрольные точки проверяются отменой, остановкой собственного процесса, отказами ввода-вывода, подменой состояния и ремонтом результатов. Параметры ограничений должны быть положительными; ограниченный проход явно помечается.

```powershell
./scripts/test-apfs-checkpoints.ps1 -Python .build/engine-env/Scripts/python.exe
```

Команда использует предоставленные примеры, не монтирует носители и не управляет окнами. Она собирает приложение и проверяет исходный вариант; новый переносимый комплект и реальные устройства требуют отдельной приёмки.
