# Восстановление по сохранившимся inode ext4

`Ext4Recovery` читает обычный локальный образ и извлекает кандидатов по сохранившейся карте удалённого inode и истории транзакций журнала JBD2. Исходник открывается только для чтения, SHA256 проверяется до и после прохода.

Обычное удаление через ядро Linux может очистить карту inode в активной таблице. В этом случае данные могут сохраниться в кольцевом буфере журнала JBD2 (транзакции до фиксации удаления) или в сохранившейся карте inode (`debugfs` / немедленный сбой). Свободные блоки могли быть перезаписаны после удаления: даже согласованные CRC метаданных не подтверждают исходное содержимое файла.

## Что проверяется

- Суперблок, версия, поддерживаемые feature flags, геометрия и границы раздела.
- Допустимые feature flags:
  - `INCOMPAT_MMP` (0x100) — multi-mount protection: безвреден для read-only восстановления.
  - `INCOMPAT_LARGEDIR` (0x4000) — каталоги >2GB / 3-уровневые htree: линейный обход каталогов ограничен лимитами и безопасен.
  - `RO_COMPAT_ORPHAN_PRESENT` (0x10000) — orphan file (inode 12): стандартен для ядер 5.15+ и безопасен для чтения.
  - `INCOMPAT_RECOVER` (0x4) — незавершённый unmount: выполняется безопасный replay журнала в оперативную память.
- CRC32C суперблока, дескрипторов, bitmap, inode и внешних extent nodes, когда включён `metadata_csum`; старый CRC16 дескрипторов при `gdt_csum`.
- Отсутствие пересечений таблиц inode и bitmap с первичными/резервными superblock и GDT, а также с метаданными других групп.
- Свободный inode, нулевой `links_count`, ненулевой `dtime` (для записей inode на диске), полностью покрытая карта данных без пересечений и циклов.
- Для кандидатов из журнала JBD2 (`journal_transaction_pre_deletion_record`): проверка целостности блока таблицы inode, проверка валидности транзакции и отсутствие коллизий со занятыми блоками в живом bitmap тома.
- Текущая незанятость каждого блока данных и внешнего узла карты (при коллизии с занятым блоком кандидат отклоняется со статусом `currently_allocated_block_conflict`).
- Ограничения объёма, количества inode, кандидатов, каталогов, узлов и результата; отмена оставляет явный незавершённый отчёт.

Поддержаны extent trees и старые direct/indirect maps. В образцах проверены прямые, одно- и двухуровневые indirect pointers, внешний extent node с физически разнесёнными блоками, 1/4 КиБ blocks, 64bit, `metadata_csum_seed`, CRC16 и раздел со смещением 1 МиБ.

`ext4/report.json` содержит исходный SHA256, inode/generation, диапазоны образа, полученный SHA256, причину отказа, список обработанных (`HandledFeatures`) и неподдерживаемых (`UnsupportedFeatures`) флагов тома, а также статус replay журнала (`JournalReplayAttempted`, `JournalReplayApplied`) и количество найденных исторических inode (`JournalHistoricalInodesFound`). `ContentAuthenticityVerified` всегда `false`; успешный файл имеет статус `deleted_inode_candidate`.

Имена из истории журнала сохраняются отдельно от текущих ссылок каталога.
У них `EntryOffset` указывает на запись в самом журнале; `JournalBlockOffset`,
`TargetBlockOffset` и `JournalTransactionSequence` разделяют источник записи,
целевой блок и транзакцию. Разные транзакции не объединяются по совпадению имени.
Для исторического блока наличие checksum-tail и проверка JBD2 не подтверждают
контрольную сумму каталога: она также зависит от inode и его generation.
Без подтверждённой связи `DirectoryChecksumVerified` остаётся `false`, а
`DirectoryPath` — неизвестным; история не строит текущую цепочку родителей.
Текущие и исторические ссылки расходуют общий `MaximumNames`; превышение
помечает отчёт как неполный. См. [формат каталогов ext4](https://kernel.org/doc/html/latest/filesystems/ext4/directory.html).

Структурные проверки этих границ находятся в `Ext4DirectoryEvidenceTests.cs`.
Они проверяют уже выделенные записи каталога и не заменяют испытания полного
native JBD2-журнала или настоящего устройства.

## Журнал JBD2 и безопасный replay в памяти

Если том был отмонтирован некорректно (установлен флаг `INCOMPAT_RECOVER` 0x4), `Ext4Recovery` выполняет симуляцию наката журнала:
1. **Поиск журнала**: внутренний журнал определяется по Inode 8 (`s_journal_inum`) через карту extents.
2. **Парсинг суперблока JBD2**: проверяются magic `0xC03B3998`, тип блока, размер блока и валидность последовательности транзакций (`s_start`, `s_sequence`).
3. **Проверка транзакции**: один ограниченный разбор используется для replay и истории. Нужен commit с тем же sequence; проверяются descriptor/revoke CRC32C, checksum каждого data tag и commit CRC32C для checksum v2/v3. Проверяются границы тегов, LAST_TAG, flags, UUID суперблока журнала и допустимые feature flags. Незавершённый хвост не считается зафиксированной транзакцией. Revocation применяется только из валидных зафиксированных транзакций, с учётом переполнения 32-битного sequence.
4. **In-Memory Overlay**: зафиксированные транзакции (дескрипторные блоки с тегами блоков и коммит-блоки) накладываются в память (`Volume.Overlay`), обновляя дескрипторы групп и битовые карты без изменения файла образа на диске. После overlay повторно проверяются CRC, границы и пересечения всех дескрипторов и bitmap; изменение геометрии superblock при online resize отклоняется. Исходный файл остаётся неизменным (гарантируется проверкой SHA256).
5. **Исторический поиск (Historical Sweep)**: сканируется весь кольцевой буфер журнала на наличие транзакций, содержащих блоки таблиц inode до удаления файла. Кандидаты, у которых на диске inode уже очищен, извлекаются из журнала при условии валидности метаданных и отсутствия коллизий блоков.
6. **Проверка коллизий**: если хотя бы один блок данных кандидата из журнала помечен как занятый в текущей битовой карте блоков тома, файл бракуется (`AllocationStatus = "currently_allocated_block_conflict"`), предотвращая выдачу чужих или перезаписанных данных.
7. **Интеграция с Evidence**: кандидаты из журнала получают контрактную метку `Kind = "ext4_journal_candidate"`, метод `"ext4 · журнал JBD2"` и статус `"Кандидат ext4 (журнал)"`.

## Имена и ограничения

Имя результата строится из смещения тома, номера inode и generation. Суффикс JPEG/PNG/GIF/WebP/PDF/ZIP выбирается только по сигнатуре текущих байтов и отмечается `ContentTypeHint=..._signature_only`. Суффикс помогает предпросмотру, но не удостоверяет тип, целостность или старое имя.

Проверенные ссылки каталогов и Unicode-имена сохраняются отдельно в `Names`. Directory entry ext4 не содержит generation inode, поэтому даже согласованная ссылка не превращается в подтверждённый исходный путь.

Не выполняются запись на диск, опасная модификация файловой системы или синтез пропущенных байтов. Sparse/unwritten maps, inline/encrypted/compressed/verity/EA inodes, bigalloc, meta_bg и неподдерживаемые features не выдаются за исходные файлы. Образ с пропусками чтения нельзя использовать для подтверждения незанятости блоков.

## Продолжение подготовки групп

Внутренний `ReadGroupsCheckpointed` сохраняет проверенные метаданные групп и
следующий номер группы. Состояние связано с SHA образа, заголовком, overlay
журнала, параметрами и кодом. Родитель подтверждает состояние до продвижения
позиции; при возобновлении восстанавливаются уже проверенные группы. Образ
при этом заново проверяется по SHA. Повреждённые сохранённые данные отклоняются.

Это компонент инициализации. Общий контроллер ext4 ещё должен соединить его с
replay/историей JBD2, поиском inode, именами и экспортом. Полное продолжение
ext4 в обычном поиске пока не заявляется. Отдельный CI проверяет этот компонент
и прежние случаи: [набор ext4](../../.github/workflows/ext4-checkpoints.yml).

`ScanInodesCheckpointed` отдельно сохраняет позицию группы/слота и исходные
байты обработанных inode. После отмены кандидаты, живые каталоги и счётчики
восстанавливаются из проверенных записей. Повторный запуск не сбрасывает общий
лимит inode. Размер порции — до 256 inode и 64 КиБ; `InodesPerCheckpoint`
позволяет уменьшить порцию, не меняя результат. Параметры входят в привязку
состояния. В нативном малом контрольном томе проверяются порции по 16 inode
и исчерпание бюджета 30; эталонный проход использует стандартную порцию 256.
Это компонент сканирования, который ещё не объединён с остальными стадиями
в полное продолжение ext4 в интерфейсе.

`TryJournalTransactionCheckpointed` сохраняет транзакцию JBD2 порциями до
64 КиБ. В сохранённых исходных блоках повторно проверяются descriptor/data/commit
CRC, теги, revoke, порядок и переход через конец кольца. Позиция внутри массива
тегов и общий бюджет восстанавливаются тем же парсером. Неполное чтение источника
вызывает ошибку, не превращается в вывод о незавершённой транзакции. Обычный
проход использует этот парсер без сохранения состояния.

Тест на журнале, записанном `debugfs journal_write`, прерывает транзакцию с
несколькими descriptors после 64 блоков по 1 КиБ. Подтверждённый префикс не
перечитывается через поток этой фазы; SHA всего источника проверяется отдельно.
Проверяются также принудительное завершение собственного процесса, реальный
отказ замены родительского файла состояния, неверные сохранённые данные,
исчерпание бюджета 70 и нативные v2/v3, revoke и переполнение sequence.
Этот компонент ещё нужно связать с общим обходом/replay/историей журнала,
именами, экспортом и контроллером сессии. Полное продолжение ext4 пока не заявляется.

`ReadJournalHistoryTransactionsCheckpointed` соединяет поиск заголовков и
проверку транзакций. Позиция обхода сохраняется порциями по 256 заголовков;
сохраняются только их первые 12 байт. Они обозначают кандидатов. До получения
списка подтверждённых транзакций парсер проверяет полные блоки, контрольные
суммы и совпадение всех descriptor/revoke-заголовков одной sequence.

Родительский журнал сохраняет ссылку на активный дочерний этап до подтверждения
его позиции. Завершённые попытки содержат ссылки на проверенные факты, а не
сериализованные объекты тома. Пути дочерних записей относительны корню этого
этапа. Общий бюджет всех попыток сохраняется после отмены; исчерпанный бюджет
не выдаёт неполный список транзакций за полную историю. Отдельный контроль
исчерпывает настоящий бюджет 252 блоков на повторных пересекающихся попытках
через несколько отмен. Это явно производная синтетическая раскладка из
нативных записей v3, а не новая проверка реального устройства.

На время обхода удерживается собственный источник только для чтения. Это
позволяет проверить SHA один раз для дочерних этапов и исключить запись или
замену файла до завершения этого обхода. При новом запуске SHA проверяется
снова. Обычный `SweepJournalHistory` использует тот же контроллер без сохранения.
`ReplayJournalCheckpointed` отдельно сохраняет последовательную цепочку от
`s_start`/`s_sequence`, активную транзакцию, общий бюджет и позицию применения
overlay. Несовпадение sequence завершает цепочку без выдуманного checksum-отказа.
Сначала проверяются все committed transactions и поздние revoke-записи; затем
подтверждённые порции до 64 КиБ применяются только к словарю блоков в памяти.
После отмены уже подтверждённая часть восстанавливается из фактов. Изменённые
блоки, контрольные суммы и несовместимое состояние отклоняются. Исходный файл
открывается только для чтения и дополнительно защищён от записи на время replay.

Нативные контроли проверяют checksum v2/v3, escape, ring wrap, поздний revoke и
переполнение sequence. Отдельный производный контроль с заново рассчитанной CRC
суперблока проверяет несовпадение sequence. Отказ замены родительского состояния,
запрет чтения источника, отмена и принудительное завершение собственного процесса
проверяются на обычных файлах. Обычный `ReplayJournal` использует тот же код без
сохранения состояния.

`SweepJournalHistoryCheckpointed` соединяет проверку транзакций и обработку
исторических inode/каталогов в одну сохраняемую стадию. Отдельные дочерние
состояния сохраняют обход транзакций и порции исходных данных до 64 КиБ. После
отмены словарь inode и список блоков каталогов восстанавливаются из проверенных
байтов. История связывается с геометрией, текущими группами, overlay и точным
набором проверенных транзакций. Повторное чтение или повреждение источника
не превращается в вывод об отсутствии данных.

Для inode сохраняются generation, sequence, физическое место в журнале и
целевой блок. Выбор последней версии учитывает переполнение sequence.
Исторические каталоги хранятся отдельно; наличие похожего блока или checksum-tail
не подтверждает старый путь и контрольную сумму каталога. Все committed revokes
учитываются до обработки данных. Состояния двух стадий подтверждаются общим
родителем. Вложенные стадии используют уже удерживаемую защиту источника;
проверка SHA повторяется при следующем запуске.

Нативные контроли проверяют v2/v3, revoke и обход кольца. Дополнительные явно
производные контроли с независимо пересчитанными inode/JBD2 CRC проверяют старую
и новую generation и блок каталога. Это обычные контрольные файлы. Ещё остаются
общий контроллер планирования и экспорта кандидатов, сохранение отчёта и контроллер ext4,
который должен связать готовые стадии с сессией. Полное продолжение ext4 в
интерфейсе пока не заявляется.

`DirectoryNamesCheckpointed` сохраняет исходные блоки каталогов и узлы карт
extent/indirect до публикации имён. Каждый блок — отдельная ограниченная порция;
запись родителя подтверждается до продвижения позиции. При продолжении тот же
парсер пересобирает имена и текущие пути из сохранённых байтов, без повторного
чтения пройденной части через поток сканирования. Полный SHA источника всё равно
проверяется при новом вызове. Состояние связано с inode каталогов, историческими
блоками, геометрией, overlay, bitmap, лимитами и исходными счётчиками предыдущих
томов. Завершение подтверждается отдельной записью с итоговыми счётчиками.

Бюджеты каталогов, байтов и имён не сбрасываются после отмены. Исторические
записи сохраняют точные ссылки на журнал, целевой блок и sequence; одинаковое
имя из другой транзакции не теряет происхождение. История не строит текущий путь
и не получает подтверждение directory CRC только по форме checksum-tail.
Текущий блок сначала полностью проверяется, затем публикуются его имена.
Также исправлены два прежних случая: блоки extent за объявленным размером
каталога не разбираются, а короткое чтение завершается ошибкой вместо отсутствия
имён. Последнее действует и в обычном проходе без сохранения состояния.

Отдельные проверки используют нативные текущие каталоги и явно синтетические
исторические записи. Контроли карты используют нативные extent/indirect узлы как
предоставленного кандидата каталога; это производный тест, не новый образ от
независимого writer. Проверяются отмена, завершение собственного процесса,
настоящие запреты чтения и замены состояния, нулевое чтение, подмена источника,
фактов, позиции и исходных параметров. Полное продолжение движка пока не принято.

`WriteFileCheckpointed` копирует подготовленную карту файла порциями до 1 МиБ.
Первые 32 байта читаются по логической карте, даже если сигнатура пересекает
физические фрагменты. Сигнатура остаётся подсказкой расширения, не проверкой
фотографии или подлинности старого содержимого. Выбор карты и проверка allocation
остаются обязанностью вызывающего этапа.

Каждая порция записывается в собственный `.partial`, сбрасывается на диск и
подтверждается родителем вместе с длиной и SHA256. После отмены проверяются
подтверждённые порции рабочей копии; исходный пройденный диапазон не копируется
заново. Полный SHA источника при новом вызове и SHA готового результата всё равно
проверяются. Состояние связано с точными extents, метаданными, именами, лимитами
и исходными счётчиками. Между возобновлениями вызывающий код должен восстановить
тот же исходный entry и baseline, а не передавать уже изменённый итоговый отчёт.

До перемещения в `files/` родитель сохраняет готовый план, размер и SHA всего
результата. Сбой перемещения оставляет этот план и рабочую копию. Если перемещение
уже произошло, но подтверждение родителя не удалось, повторный вызов проверяет
готовый файл и завершает публикацию без повторного чтения карты источника.
Пропавшую рабочую копию или результат можно построить из той же карты, проверяя
каждую порцию по сохранённым SHA. У такого восстановления есть собственная
сохраняемая позиция, поэтому его тоже можно отменить и продолжить.

Повреждённые существующие файлы сохраняются и отклоняются. Неподтверждённый хвост
после сбоя сравнивается с соответствующей порцией источника до замены; неизвестный
хвост не удаляется вслепую. Рабочие файлы создаются с уникальными именами через
`CreateNew`. Также исправлена старая очистка `WriteFile`: при неудачном `CreateNew`
она больше не удаляет уже существовавший чужой `.partial`.

Проверки копирования используют собственные разнесённые диапазоны с независимой
побайтовой сборкой, одно- и многопорционные файлы, карту из нативного ext4-отчёта,
сбои чтения/записи/перемещения и родителя, отмену и остановку собственного процесса
при копировании и восстановлении пропавшего результата. Подмена карты, имён,
счётчиков, лимитов, источника, рабочей копии и готового файла отклоняется.
Это дочерний компонент: общий обход кандидатов, отчёт и подключение всей цепочки
к `RecoverySession` ещё нужны для полного продолжения ext4.

## Воспроизвести без WSL и сети

В `tests/fixtures/ext4` сохранены 60 сжатых синтетических образов и manifest с SHA256 сжатых и исходных файлов. Файловая система создана настоящими `mke2fs`/`debugfs` 1.47.3. Старые `journal-*` содержат вручную записанные JBD2 записи. Новые 18 `native-journal-*` используют настоящий `debugfs journal_open/journal_write`; повреждения CRC, flags и перенос через конец кольца явно отмечены как производные синтетические контроли. Команды, хеш нативного образа до очистки inode и хеш logdump сохранены в manifest; бинарные программы и пользовательские данные в комплект не входят.

`PROVENANCE.txt` описывает происхождение синтетических данных и не задаёт отдельную лицензию.

Из корня подготовленного checkout с Python-окружением сборки:

```powershell
$run = [Guid]::NewGuid().ToString('N')
./scripts/test-ext4-checkpoints.ps1 -Python .build/engine-env/Scripts/python.exe `
    -FixtureRoot ".build/ext4-fixtures-$run" -EvidenceDirectory ".build/ext4-checks-$run"
```

Команда собирает всё приложение и запускает двенадцать программ проверок: группы,
inode, транзакции JBD2, связанный обход журнала, replay, исторические записи,
продолжение поиска имён и копирования файла, защиту существующих результатов,
чтение метаданных, 60 прежних образов и происхождение имён. Она не открывает интерфейс и не запрашивает
права администратора.
Нужны новые папки образцов и результатов; в результатах сохраняются журналы
и `receipt.json` с SHA приложения. Для повторного использования проверенных
образцов укажите их папку и `-SkipFixtureExtraction`.
Распаковщик проверяет имена, размеры, SHA256 и ограничивает объём; WSL не
вызывается. Сеть для этого набора не требуется, но команда не блокирует сеть
всей машины. Готовая пользовательская программа не требует WSL или Python.

Чтобы заново получить образцы внешними инструментами, нужен уже установленный WSL `docker-desktop` с `mke2fs` и `debugfs`. Генератор не монтирует образы, не устанавливает пакеты и не меняет службы:

```powershell
$generatedRoot = '.build\ext4-generated-' + [Guid]::NewGuid().ToString('N')
& .build\engine-env\Scripts\python.exe tests\ext4_fixture_generator.py --destination $generatedRoot --distribution docker-desktop
```

## Доказательства и границы проверки

| Доказательство | Вывод | Где проверить |
|---|---|---|
| Контрольный набор на 60 образах | Положительные случаи совпадают с независимым payload SHA256, флаги MMP/largedir/orphan_present обрабатываются, replay и historical inode работают, повреждённые/неподдерживаемые карты не экспортируются | `tests/Ext4RecoveryTests.cs`, manifest |
| Тот же набор после offline-распаковки | Поддерживаемый набор воспроизводится без вызова Linux-инструментов | `ext4_fixture_generator.py --extract` |
| 18 workflow checks | Реальный конвейер, каталог, сохранение/возобновление прохода, защита от пропусков чтения и выбор ext4 в настройках работают совместно | `tests/Ext4WorkflowTests.cs` |
| 28 независимых integration audit checks | Противоречивые отчёты, неверная привязка к источнику, неполные карты и изменённые файлы не получают прежнее происхождение; дубликат PhotoRec сохраняет ссылку ext4 | `tests/Ext4IntegrationAuditTests.cs` |
| Нативные JBD2 checksum v2/v3 и отрицательные контроли | Валидный replay/history, несколько descriptors, escape, ring wrap; отсутствие commit, CRC bitflip descriptor/data/commit/revoke, revoke с переполнением sequence и неподдерживаемые flags не экспортируют старый inode | `native-journal-*`, per-case provenance в manifest |
| Replay и historical sweep JBD2 | Восстановление удалённого файла из транзакции журнала при затёртом на диске inode; отказ при коллизии блока с занятым | `journal-dirty-replay`, `journal-historical-deleted`, `journal-historical-conflict` |
| Толерантность к benign флагам | Тома с `INCOMPAT_MMP`, `INCOMPAT_LARGEDIR` и `RO_COMPAT_ORPHAN_PRESENT` безопасно сканируются и извлекают файлы | `mmp-feature-tolerated`, `largedir-feature-tolerated`, `orphan-present-tolerated` |
| Мутации указателей с заново рассчитанными CRC | Пересечения, неизвестные features, неверные bounds и циклы отклоняются независимо от раннего checksum-отказа | Случаи `*-valid-crc` в manifest |
| Содержимое свободного блока изменено после удаления | Выдаются текущие байты как кандидат; исходное содержимое не угадывается | `free-data-overwritten` |

Журнал ограничен 256 МиБ и 262144 блоками, обход транзакций и кольца имеет общий бюджет. Fast commit, внешний журнал, неизвестные или несовместимые journal feature flags, устаревший DELETED tag и изменение геометрии при replay не поддерживаются. Checksum v2/v3 проверены нативным writer; legacy transactional CRC32 реализован по исходнику JBD2, но нативным контрольным образом отдельно не подтверждён.

В независимом локальном oracle `debugfs journal_run` валидный v3-журнал восстановил 70001 байт с тем же SHA256; вариант с повреждённым commit и отозванным блоком сохранили inode без полезной нагрузки. Это отдельное доказательство e2fsprogs, не тест физического устройства.

Это тесты обычных образов. Восстановление на физических устройствах, удаление через реальное ядро, все варианты ext4 и результаты платных конкурентов этими проверками не подтверждаются.

Первичные форматы: [ext4 checksums](https://docs.kernel.org/filesystems/ext4/checksums.html), [group descriptors](https://docs.kernel.org/filesystems/ext4/group_descr.html), [extent/indirect maps](https://docs.kernel.org/filesystems/ext4/ifork.html), [JBD2 journal](https://docs.kernel.org/filesystems/ext4/journal.html), [e2fsprogs 1.47.3](https://git.kernel.org/pub/scm/fs/ext2/e2fsprogs.git/tree/?h=v1.47.3)
