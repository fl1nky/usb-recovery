# Сохранившиеся записи Telegram

Анализ работает с доступными локальными файлами. Он не получает закрытый дамп RAM телефона, не обходит блокировку устройства и не расшифровывает Desktop `tdata`. Предыдущая версия или текстовый фрагмент сами по себе не доказывают удаление сообщения

## Как запустить

1. Открой **Telegram → Анализировать** для поиска в доступных локальных каталогах компьютера
2. Для своей копии выбери **Источник… → Папка / копия телефона…** либо **Дамп памяти / файл…**, затем **Анализировать**
3. Введи слова и нажми **Найти**; для регулярного выражения включи **Regex**
4. Используй категорию **Удалённые записи (остатки)** и смотри происхождение выбранной строки. Категории **Предыдущая версия** и **Текстовый фрагмент** проверяй отдельно

Для Android SQLite нужны читаемая база с поддерживаемой схемой `messages_v2`/`messages_topics` и сохранившиеся файлы с тем же именем `-wal`/`-shm`, если они есть. Передавай согласованную неподвижную копию, а не открытую изменяющуюся базу. Дамп `.dmp/.mem/.hprof/.raw/.bin` необходимо предоставить самостоятельно; позиции в нём являются смещениями файла, не адресами оперативной памяти. Экспорты JSON/HTML также остаются поддерживаемыми источниками

Сначала создаётся рабочая копия с SHA256. SQLite/TL разбираются на ней; исходная база не открывается для записи, не checkpoint-ится и не очищается через VACUUM

## Что означает найденное

| `record_kind` | `recovery_status` | Категория и допустимый вывод |
|---|---|---|
| `sqlite_deleted_record` | `deleted_supported_by_evidence` | `backup`; строка сохранилась в свободной области страницы, доказанно принадлежащей таблице, но отсутствует в текущей таблице. Ручное удаление пользователем не установлено; `deleted=null` |
| `sqlite_deleted_record` | `previous_version_residual` | `previous`; сохранилось другое содержимое уже существующего ключа |
| `tl_message` с `residual_sources` | Один из двух статусов выше | Полная запись уже подтверждена независимым committed-снимком; сведения об остатке добавлены к ней без дублирования и потери прежнего доказательства |
| `sqlite_wal_residual` | `unattributed_structured_fragment` | `fragment`; поддерживаемое TL-тело найдено в заменённой, ранее зафиксированной странице WAL; принадлежность исторической таблице/аккаунту не подтверждена |
| `sqlite_residual_fragment` | `unattributed_structured_fragment` | `fragment`; TL-тело на свободной странице, прежний владелец которой неизвестен |
| `typed_tl_fragment` | `unattributed_structured_fragment` | `fragment`; поддерживаемое TL-тело в предоставленном дампе |
| `memory_fragment` | Не задаётся | `fragment`; найденная строка без подтверждения формата Telegram |

У неатрибутированных фрагментов настоящие `chat_id`, `message_id`, `sender_id`, `timestamp` остаются неизвестными. Декодированные значения находятся только в `candidate_message_id`, `candidate_peer`, `candidate_date`. Фильтр `deleted` — отдельный выбор по `recovery_status`, а не новый тип `evidence_kind`; исходные категории `export`/`backup`/`previous`/`fragment` сохраняются

Для структурной записи должны совпасть SQL `mid/uid/date` и поля строгого TL-разбора. Активные строки не выдаются за остатки. При слиянии freeblocks допускается восстановить только вычисляемую длину заголовка из сохранившихся serial types; содержимое, ключи и неизвестные serial types не подбираются

## Как проверить происхождение

- `source_file`, `source_sha256`, `snapshot_id`, `source_record` связывают результат с исходной копией и записью
- `byte_offset` с `offset_kind=sqlite_logical_file_byte` относится к логическому образу SQLite. `physical_source` (`db`/`wal`) и `physical_byte_offset` указывают реальные байты соответствующего файла
- `sqlite_page`, `sqlite_region`, `sqlite_record_page_offset`, `sqlite_blob_page_offset`, `sqlite_record_length`, `sqlite_record_sha256` описывают проверенную область; `sqlite_header_length_reconstructed` отмечает восстановленную длину заголовка
- Для WAL сохраняются `wal_sha256`, `wal_frame`, `wal_commit_frame`; для полного предыдущего снимка — также его SHA256 и `wal_proof`. Незавершённые транзакции не становятся committed-историей
- `native_tl_body_sha256` идентифицирует проверенное TL-тело. Совпадение текста не используется как доказательство одинаковых сообщений; дополнительные физические следы сохраняются в `residual_sources`

SHA256 фиксирует полученные байты и позволяет обнаружить их изменение; он не доказывает подлинность переписки. Неполная карта, неизвестная схема или исчерпание лимита отражаются в замечаниях. Лимиты нового разбора: до 262144 страниц, 256 МиБ сканируемого свободного пространства, 20000 результатов и 64 МиБ суммарных записей; достижение предела не считается полным проходом

## Почему часто ничего не остаётся

Официальный Android Telegram в закреплённом [MessagesStorage.java](https://github.com/DrKLO/Telegram/blob/4de548e79fed27f1a66fbdff84223321838fe925/TMessagesProj/src/main/java/org/telegram/messenger/MessagesStorage.java#L304) включает `PRAGMA secure_delete=ON`. Поэтому положительные freeblock-примеры с `secure_delete=OFF` показывают восстановление сохранившихся старых/иных копий, а не гарантированный результат на современном телефоне. Отдельно могут уцелеть предыдущие committed WAL-страницы. После затирания, VACUUM или перезаписи соответствующих байтов этот разбор не придумывает сообщения

## Доказательства и воспроизведение

На исходниках пройдены **150 тестов**: прежние 126 и новые [TelegramDeletedTests.py](../../tests/TelegramDeletedTests.py) — 24. Покрыты реальные SQLite DELETE и объединение freeblocks, официальные 20-колоночные схемы, страницы 512/4096/65536 байт, UTF-16LE/BE, secure-delete/VACUUM/перезапись, несовпадение ключей и секретные диалоги, контрольные суммы/соли/коммиты WAL, текущий WAL-overlay, отмена, лимиты, изменение источника и TL через границу блока дампа. Полный набор задаётся в [build-helper.ps1](../../scripts/build-helper.ps1)

Из корня подготовленной среды разработчика новый набор запускается так:

```powershell
.\.build\engine-env\Scripts\python.exe tests\TelegramDeletedTests.py
```

Проверка нового переносимого EXE/helper выполняется отдельно; эти 150 тестов относятся к исходникам. Настоящие пользовательские телефоны, RAM и личные переписки в этих испытаниях не использовались

Реализация: [sqlite_deleted.py](../../helpers/recovery_engine/sqlite_deleted.py), [telegram_auto.py](../../helpers/recovery_engine/telegram_auto.py), [telegram_tl.py](../../helpers/recovery_engine/telegram_tl.py), [memory_fragments.py](../../helpers/recovery_engine/memory_fragments.py). Формат хранения: [официальная спецификация SQLite](https://sqlite.org/fileformat2.html); прежние снимки: [sqlite_history.py](../../helpers/recovery_engine/sqlite_history.py)
