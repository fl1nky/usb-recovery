# Устройство проекта

Приложение на C# и WinForms управляет источниками, фоновыми операциями и результатами. Локальный Python-обработчик занимается Telegram, изображениями и поддерживаемыми зашифрованными копиями; в готовом выпуске он уже собран вместе со своими зависимостями

| Каталог | Ответственность |
|---|---|
| `src/Recovery/UI` | Окна, панели и отображение прогресса; общие элементы — в `UI/Controls` |
| `src/Recovery/Recovery/Engines` | Поиск по файловым системам, сигнатурам, архивам, фрагментам и тексту |
| `src/Recovery/Recovery/Results` | Проверка содержимого, фотографии, каталог, происхождение и экспорт |
| `src/Recovery/Media` | Изолированный проход локального видео через Media Foundation, ограничения процесса и мягкая оценка декодирования |
| `src/Recovery/Recovery` | Параметры, порядок этапов, измеряемый прогресс и продолжение сессии |
| `src/Recovery/Storage` | Подготовка APFS/BitLocker, сборка RAID и поиск после подготовки |
| `src/Recovery/Infrastructure` | Съём образа, запуск обработчика, анализ Telegram и пути ресурсов |
| `src/Recovery/Sources` | Общий интерфейс источника, логические файлы, телефон и рабочие копии |
| `src/Recovery/Interop` | Низкоуровневое взаимодействие с Windows WPD/MTP |
| `helpers/recovery_engine` | Локальный Python-обработчик и закрепление зависимостей |
| `scripts` | Сборка, упаковка, проверки и единые пути проекта |
| `tests` | Синтетические проверки и разрешённые опубликованные образцы |

`Program` содержит точку запуска. `RecoveryHub` переключает разделы, `RecoveryForm` ведёт поиск на флешке или образе, а `LogicalRecoveryPanel` отвечает за импорт логических источников. `StorageRecoveryPanel` собирает параметры и показывает состояние; подготовку, сборку и последующий поиск выполняет `StorageRecoveryWorkflow`

## Как проходят данные

Физическая флешка сначала читается в образ; последующий поиск работает с копией. `RecoveryPipeline` запускает выбранные методы, а `RecoverySession` связывает этапы с SHA256 образа и проверяет сохранённые результаты перед продолжением. `RecoveryCatalog` объединяет одинаковое содержимое, сохраняет происхождение и проверяет байты при экспорте

Папки и телефоны проходят через `IRecoverySource` и отдельное копирование доступных файлов. Они не направляются в посекторный FAT/NTFS-поиск. APFS извлекается в отдельные файлы; BitLocker и RAID сначала подготавливают логический образ, по которому затем можно запускать обычный поиск

Пароли и ключи передаются обработчику через перенаправленный стандартный ввод. Исходный носитель не используется как папка результатов; незавершённый файл и успешно опубликованный результат имеют разные состояния

## Где находятся файлы

`scripts/ProjectPaths.ps1` задаёт `src/Recovery`, `.build/app`, `dist/USB-Recovery`, `tests` и `tools` для всех сценариев. `ApplicationPaths` находит ресурсы рядом с переносимым EXE; для документированных разработческих папок `.build/app` и `.build/tests` он использует корень проекта

Сборки, временные образы, результаты проверок и предыдущие комплекты остаются в `.build`; переносимый выпуск — в `dist`. Эти данные, каталоги сторонних исполняемых файлов и большие офлайн-зависимости исключены из Git. Пользовательские данные не становятся исходниками проекта

Текущие инструкции находятся в [руководстве по сборке](build.md) и `docs/guides`. Старые отчёты сохранены в [архиве](../history/README.md); они описывают конкретные прошлые сборки и не заменяют проверку текущей

Фото-поиск связывает неизменяемые поколения `recovery_checkpoint.py` с контрольной точкой в `RecoverySession`. Parent подтверждает хеш поколения через ограниченный NDJSON-протокол; при продолжении helper проверяет источник, исполняемый код, зависимости, карты и сохранённые изображения. Файлы состояния и карантин отделены от каталога/галереи. `recovery-run.lock` ограничивает один активный поиск в папке

Поиск в переписках отделён от чтения полного сообщения. `archive_search.py` выдаёт фрагмент вокруг настоящего совпадения и координаты в символах Unicode. `archive_text.py` читает полную запись страницами по 65 536 символов; ссылка содержит тип индекса, позицию и SHA256 исходной записи. Изменённая запись требует повторного поиска. Оба пути читают только готовый локальный архив, без изменения DB/WAL/SHM и загрузки внешнего HTML

`ArchiveSearchService` проверяет ограниченный протокол обработчика, UTF-8, пары суррогатов, координаты и размер страницы. `ArchiveMessageTextForm` показывает полный текст частями и отменяет чтение при закрытии. Проверки искусственного обработчика отделены от испытаний настоящего переносимого helper
