# Продолжение сборки MP4 и MOV

В основном запуске фрагментированное видео продолжает сохранённую попытку после
отмены, остановки процесса и ошибок чтения или записи. Реализация находится в
ветке разработки; обновление опубликованного переносимого комплекта проверяется
отдельно. Сборка структуры не подтверждает подлинность содержимого или факт удаления.

## Продолжить поиск

Сохрани всю рабочую папку поиска вместе с `usb.dd`, `recovery-session.json` и
`fragmented-media.state`. Используй обычное продолжение поиска в приложении.
Завершённый этап используется повторно только после проверки его файлов.
Не переноси отдельную контрольную точку в другой поиск и не редактируй её вручную.

Если старый незавершённый запуск не сохранил подтверждённую точку, программа
переносит его результат и состояние в `attempt-history`, затем начинает новую
попытку. Изменённый источник или повреждённое подтверждённое состояние вызывают
ошибку; программа не скрывает её перезапуском с нуля.

## Что сохраняется

| Часть | Файлы и поведение |
|---|---|
| Чтение и разбор | Неизменяемые блоки прочитанных данных, их SHA256, порядок запросов и маркер конца. При продолжении парсер повторяет вычисления по сохранённым байтам; подтверждённые запросы не читают исходный образ заново |
| Кандидат | План размещения и текущий блок копирования. Незавершённое тело остаётся `.partial` вне каталога результатов |
| Публикация | Имя `candidate-<SHA256>.mp4` появляется после полного копирования и проверки. Для fMP4 дополнительно сверяется ожидаемый хеш сборки |
| Совпадения | Одинаковое содержимое проверяется и используется повторно. Посторонний файл с тем же именем не перезаписывается |
| Итог | Сначала подтверждается план отчёта, затем публикуется `fragmented-media.json`. Отказ сохранения родительской сессии не теряет предыдущую подтверждённую точку |

Исчезнувшее тело завершённого кандидата можно заново собрать по подтверждённому
плану. Изменённое существующее тело сохраняется и вызывает ошибку.
Рабочая папка растёт за счёт сохранённых прочитанных байтов и журнала; следует
заранее оставить место на другом носителе. Полная проверка SHA256 образа при
открытии сессии остаётся необходимой, даже когда повторного копирования нет.

## Проверить реализацию без устройств

Из корня репозитория, с подготовленным Python 3.12/Pillow и компилятором .NET Framework:

```powershell
./scripts/test-media-checkpoints.ps1 -Python python
```

Каждый повтор требует нового `-EvidenceDirectory`. Скрипт проверяет контрольные
образы из репозитория, собирает приложение и запускает:

- `MappedContentCheckpointTests`: имя по хешу, ожидаемый SHA256, отмена, совпадающий
  и изменённый файл, сохранение старого формата идентичности планов APFS/ReFS
- `FragmentedMediaCheckpointTests`: равенство прежнему результату, возобновление,
  принудительная остановка собственного процесса, ошибки чтения и подтверждения,
  подмена источника, карт чтения, параметров и состояния, ремонт отсутствующего выхода
- `FragmentedMediaSessionCheckpointTests`: основной запуск, сессия, каталог,
  сохранение прежней попытки и проверка завершённых файлов
- Прежние проверки QTFF, AVC/AAC по блокам, HEVC и индексированного fMP4

Отчёты и журнал каждой проверки сохраняются в `.build/media-checkpoint-evidence`.
Проверки сравнивают байты, SHA256 и карты размещения с контрольными образцами.
Этот запуск не выполняет внешний видеодекодер, не подключает устройства и не
доказывает поддержку любой фрагментации или окончательную потерю ненайденных данных.

## Где менять код

Основной путь: `RecoveryPipeline` → `RecoverCheckpointed` → `EngineCheckpoint` →
`RecoveryMetadataReads` и `RecoveryMappedFilePublisher` → `RecoverySession` → каталог.

- `FragmentedMediaRecovery.cs`, `.Units.cs`, `.Ranges.cs`, `Fmp4Recovery.cs`:
  распознавание, геометрия, бюджеты и прежний самостоятельный API
- `FragmentedMediaRecovery.Engine.cs`: общий порядок стадий, дочерние точки,
  подтверждение файлов и публикация отчёта
- `FragmentedMediaRecovery.CheckpointAdapters.cs`: привязка плана кандидата,
  подключение сохранённого чтения и копирования
- `FragmentedMediaRecovery.ReadMaps.cs`: неизменность доступных карт ошибок чтения
- `RecoveryMappedFilePublisher.cs`: общий для APFS, ReFS и видео механизм записи;
  новые возможности имён и ожидаемого SHA256 включаются явно

При изменении общего механизма записи также нужны проверки APFS и ReFS.
