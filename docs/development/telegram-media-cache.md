# Подписи к фотографиям в Android media_v4

Адаптер читает 19 явно поддержанных форматов Message и пять photo-media конструкторов из медиакэша Telegram Android и проверенных committed WAL-снимков. Сохраняются текст сообщения и отдельная старая подпись к фотографии. Удаление строки кэша не доказывает удаление переписки пользователем; `deleted` остаётся `null`.

## Проверить на синтетических данных

Из корня проекта с подготовленным разработческим Python:

```powershell
python tests/TelegramMediaCacheTests.py
python tests/TelegramMediaCacheProfileTests.py
python tests/build_telegram_media_cache_fixtures.py .build/media-cache-fixtures
```

Каталог назначения генератора должен отсутствовать. Генератор не импортирует recovery-код: собственные строки кодируются по официальному формату, настоящая SQLite WAL создаётся при `secure_delete=ON`, SQL-эталон сохраняется до удаления. Согласованные DB/WAL/SHM копируются при остановленном писателе. В manifest закреплены SHA генератора и исходных DB/WAL/SHM. Это проверка собственных образцов, а не настоящего Android.

`scripts/test.ps1` готовит отдельный корпус из 17 случаев и запускает обязательный `TelegramMediaCachePortableTests` через собранный helper и публичный сервис программы. Проверяются ключевые слова, Regex, полный Unicode-текст, WAL, дополнительные источники, повторный импорт и неверные данные. Старый или изменённый корпус сохраняется и отклоняется; результаты предыдущей сборки не заменяют новый запуск.

Дополнительный `TelegramMediaCacheProfilePortableTests` использует 855 BLOB из независимого официального Java writer и шесть SQLite-снимков. Эталонные входные строки заданы до запуска recovery parser. Проверяются обе текстовые роли, даты и идентификаторы, Unicode-поиск, отдельный полный текст, WAL, остатки страниц и повторный импорт. Источники, лицензия и SHA находятся в [корпусе](../../tests/fixtures/telegram-cache-profiles/README.md). Java-набор проверяет сериализацию с `PhotoEmpty`, не запуск приложения Android и не все вложенные варианты фотографий.

## Формат и проверка

Формат закреплён официальным [commit 4de548e](https://github.com/DrKLO/Telegram/commit/4de548e79fed27f1a66fbdff84223321838fe925).

- [MessagesStorage.java](https://github.com/DrKLO/Telegram/blob/4de548e79fed27f1a66fbdff84223321838fe925/TMessagesProj/src/main/java/org/telegram/messenger/MessagesStorage.java#L559-L561): пять столбцов `mid`, `uid`, `date`, `type`, `data`; составной ключ `(mid, uid, type)`.
- [MediaDataController.java](https://github.com/DrKLO/Telegram/blob/4de548e79fed27f1a66fbdff84223321838fe925/TMessagesProj/src/main/java/org/telegram/messenger/MediaDataController.java#L4556-L4562): BLOB декодируется как полное сообщение.
- [DatabaseMigrationHelper.java](https://github.com/DrKLO/Telegram/blob/4de548e79fed27f1a66fbdff84223321838fe925/TMessagesProj/src/main/java/org/telegram/messenger/DatabaseMigrationHelper.java#L990-L1034): миграция переносит старые BLOB в `media_v4` без повторной сериализации.

Читатель требует точный порядок, SQL-типы и ключ. Дополнительные, generated, виртуальные и `WITHOUT ROWID` схемы отвергаются. Поддержан только `type=0` с полностью прочитанным photo-media сообщением. Точный список 19 конструкторов между слоями 118 и 232 закреплён в `_MESSAGE_PROFILES` [адаптера](../../helpers/recovery_engine/telegram_media_cache.py); промежуточные неизвестные версии автоматически не разрешаются. Слой 114 для фото не поддержан. Конструктор, положительный SQL `mid`, `uid` и `date` сверяются независимо. Секретные dialog IDs, неизвестные flags и вложенные поля или другие медиа не интерпретируются догадкой.

Подпись сохраняется как `telegram_media_cache` с состоянием `current_cache_record` либо `historical_cache_record`. История получает привязку к проверенному WAL commit и хешам снимка. Непроверенный WAL не доказывает текущее состояние. Исходный DB/WAL/SHM не меняется; SQLite открывает рабочую копию.

`text_field=message` обозначает основной текст, `media.legacy_caption` — старое поле подписи. Если обе строки непустые и различаются, подпись сохраняется дополнительной записью `telegram_media_cache_caption`. Если основной текст пустой, подпись остаётся основной записью с собственной ролью; равные строки не дублируются. Роль сохраняется также для основных и остаточных native-записей, поиска, JSONL, повторного импорта и HTML. Интерфейс объясняет, что это два поля одной записи; счётчик текстовых записей не равен числу разных сообщений.

## Происхождение и объединение

Путь данных: `Analyzer.sqlite` → `telegram_media_cache.photo_captions` → строгий TL-reader → публикация с происхождением кэша.

Совпадение подтверждённых source/account scope, dialog/message IDs, полного TL-body SHA и текстовой роли позволяет объединить кэш с основной записью. Основная запись сохраняет свои статус, текст и доказательства; кэш добавляет источник. Разные байты при одинаковых IDs и разные аккаунты не объединяются, в том числе при одинаковом тексте и различном `edit_date`. Повторные кэш-источники ограничены десятью; достижение предела отмечается. Kind, status, полный body SHA, роль и привязка к WAL сохраняются также в дополнительных источниках и повторном импорте.

Внутренний индекс проверенных SQL/TL-объектов не формируется из полей предоставленного JSON. При импорте готового архива происхождение помечается `provided_archive_metadata`. Заявленная отметка об удалении сохраняется в ограниченном `archive_claims`, но получает статус `imported_recovery_claim` и не включается в фильтр и счётчик новых проверенных остатков. Интерфейс и локальный HTML отдельно объясняют эти отметки.

Остаток SQLite привязывается к существующему тексту только через проверенный внутренний объект, совпадающие TL-body SHA и роль. Заявленный хеш в готовом JSON не позволяет приложить физическое доказательство к другой строке.

Фото-метаданные не означают наличие фотографии: сохраняется `photo_reference_only`, Android attachment path не разрешается, изображение из этого кэша не извлекается. Отсутствующие имена автора остаются неизвестными.

## Границы

Адаптер не исследует свободные блоки, произвольные дампы, зашифрованные источники, профили или устройства. Затёртые байты не восстанавливаются. Secure-delete positive относится к сохранившейся ранней WAL-версии, а не к чтению затёртой текущей страницы.

Цепочка доказательств: официальная схема → независимый SQLite/SQL-эталон → исходные тесты → отдельная сборка helper и portable-приёмка. Компиляция теста или приёмка прежнего runtime не доказывает прохождения новой сборки. Наличие кэша не гарантирует восстановление всей удалённой истории.

## Проверенный переносимый комплект

Новый helper прошёл `TelegramMediaCacheProfilePortableTests`: все 855 независимых Java-примеров дали 1235 отдельных текстовых полей, включая 665 основных текстов и 570 старых подписей. Проверены шесть снимков, поиск, Regex, полный текст и повторный импорт. Дополнительный сценарий подтверждает: предоставленная ложная строка с настоящими идентификаторами и хешем тела сохраняется отдельно и не получает доказательство из SQLite/WAL. Слабые текстовые фрагменты проверяются своей категорией, с неизвестными чатом, автором и датой.

Весь комплект прошёл 59 основных offline-наборов, четыре набора Telegram и один USB-конвейера. Python отсутствовал в PATH; временные правила блокировали сетевые подключения проверяемых процессов и были удалены после прогона. Это тестовые копии и переносимый Windows EXE, не работа на настоящем Android/iPhone.
