# Компактная таблица размеров видео

`stz2` хранит размеры кадров в 4, 8 или 16 бит вместо обычной 32-битной таблицы `stsz`. Это отдельное расширение классического MP4/MOV; поддержка `moof`, нескольких `mdat` и произвольных разрывов внутри кадров из него не следует. Разбор таблицы не подтверждает, что видео удалено, а содержимое кадров подлинно.

## Проверить образцы

Из корня исходников, в среде разработчика:

```powershell
python -B tests/prepare_stz2_media_fixtures.py .build/video-stz2-fixtures-current
python -B tests/prepare_stz2_media_fixtures.py --verify .build/video-stz2-fixtures-current
```

Первый запуск распаковывает проверенные собственные образцы. Повторный проверяет все файлы; `--verify` ничего не создаёт. Изменённый, неполный или дополненный каталог отклоняется без исправления. Python пользователю готовой программы не требуется.

## Что доказывают образцы

В `tests/fixtures/video-stz2/manifest.json` находятся 4 случая: настоящие AVC и HEVC hvc1, каждый с обычной таблицей и эквивалентом `stz2/16`. Исходные MP4 созданы закреплённым FFmpeg из тестового изображения. Перепаковка хвостового `moov` меняет только представление таблицы и размеры её родителей; байты кадров и их смещения сохраняются.

Для каждого кодека независимый FFmpeg декодировал одинаковые 12 кадров в обеих версиях. `ffprobe` подтвердил одинаковые размеры, смещения, времена и SHA256 всех пакетов. Архив содержит оригиналы, `framemd5`, пакетный журнал, карты физических диапазонов и хэши. Проверка каждого возможного начала целого блока данных оставляет одно размещение в каждом образе размером 1 MiB; это не доказательство для произвольных разрывов внутри блока.

`table-oracles.json` содержит отдельно 7 положительных проверок упаковки 4/8/16 бит и 12 отрицательных проверок строгой политики. Они не являются дополнительными декодированными видео. Контроль `reject-count-8193` содержит только 3 байта данных вместо полной таблицы: он проверяет неполную длину, а не превышение общего предела кадров. У 4-битных записей старшая половина байта идёт первой; при нечётном числе записей последняя младшая половина не относится к кадру. Положительный контроль с ненулевыми неиспользуемыми битами не должен превращаться в лишний кадр.

Основа формата: [FFmpeg n8.0](https://raw.githubusercontent.com/FFmpeg/FFmpeg/n8.0/libavformat/mov.c) и [Bento4](https://raw.githubusercontent.com/axiomatic-systems/Bento4/master/Source/C%2B%2B/Core/Ap4Stz2Atom.cpp). Чтение этих реализаций не даёт основания требовать нулевые неиспользуемые биты; некоторые остальные строгие проверки здесь являются политикой восстановления, а не доказанным отказом стороннего декодера.

## Граница результата

Образцы фиксируют конкретный пробел выпуска 663: его обязательный `One(stbl,"stsz")` отклонял `stz2`-only до поиска кадров. При изменении парсера должны сохраниться ограничения размера, времени, отмены, полного покрытия и неоднозначности. Оригинальные SHA и карты используются только для проверки результата, а не выбора при восстановлении. Подготовка этих данных сама по себе не является приёмкой новой готовой сборки или испытанием реальной флешки.

Парный локальный прогон на тех же полных образах дал следующие точные совпадения с оригиналами:

| Собственный образец | Выпуск 663, app FE7 | Новая сборка из исходников |
|---|---:|---:|
| AVC, `stsz` | 1 | 1 |
| AVC, `stz2/16` | 0 | 1 |
| HEVC hvc1, `stsz` | 1 | 1 |
| HEVC hvc1, `stz2/16` | 0 | 1 |

Это проверка исходников на четырёх искусственных образах, без сравнения с платными программами и без реального устройства. SHA256 парного отчёта: `aa371fef221c8a335c66bb330983ef2fcfb2a534f5bfcd4b1be3003bb440d66b`; новой проверенной программы: `54849740ca26a4496a16bb1c9f8cdd987af1700e22d2c4c4021907982f160061`. Эти числа не заменяют приёмку переносимого комплекта, общий прогон и публикацию нового выпуска.
